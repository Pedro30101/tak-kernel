**Astros** is the graphical desktop environment built into the TAK Kernel. This repository contains an experimental x86-64 operating-system project that boots through GRUB/Multiboot2, loads its initial files from an initramfs, and starts either the live desktop or the installed-system login screen.

> **Project status:** experimental, very broken and unfinished. It is for development and testing, not for storing sensitive data or use as a secure, production operating system.

## What works today

- GRUB Multiboot2 boot, with BIOS/UEFI boot files assembled by the ISO build.
- A graphical desktop and window manager (the taskbar can be moved with the `taskbar` terminal command), keyboard/mouse input, terminal, settings, task manager, system info, and file manager.
- A virtual filesystem populated from the initramfs, plus a native BFRUS filesystem, FAT32 EFI boot support, and ATA/IDE storage.
- Kernel-managed tasks and a restricted `.te` user-program format.
- A limited x86-64 ELF64 loader with a small Linux syscall layer (see "User executable formats").
- Built-in applications: text editor, TIDE Studio, image viewer (via stb_image), WAV media player, task manager, settings, and the installer. Sample `.te` apps (calculator, paint, snake, hello) are in `apps/`.
- A login/registration screen with a salted, iterated SHA-256 password check.
- Framebuffer-based display support on systems with **Intel, AMD, and NVIDIA** graphics, as well as several virtual display adapters. The kernel identifies these vendors through PCI; drawing uses the framebuffer supplied by the bootloader, not vendor-specific 3D acceleration drivers.

TIDE Studio is a small code editor with Python and C tabs, syntax highlighting, and a built-in interpreter (`src/py.c`) that runs simple scripts. It is still early and very limited.

### Not included in this release

- No wifi drivers.
- No TLS and no Linux socket API.
- No Steam connectivity.

### Networking and security limitations

The kernel has a polling driver for Intel 82540EM/E1000 adapters (`8086:100e`), with bounded RX/TX DMA rings and Ethernet-frame I/O. A small network stack adds ARP caching/replies, bounded IPv4 receive/transmit, ICMP echo replies, DHCP address configuration, DNS A-record lookup (`dns <hostname>`), and a single bounded TCP client used by `http-get <hostname> <path>` for unencrypted HTTP on port 80. `net-info` reports the adapter, link state, frame counters, and DHCP-provided IPv4 configuration. The default QEMU run uses an E1000 adapter; VirtualBox can use its Intel PRO/1000 MT Desktop (82540EM) adapter. DMA is restricted to the driver's fixed rings/buffers but is not isolated by an IOMMU. TLS, Linux socket calls, and Steam connectivity are not implemented.

Security is also **unfinished**. The account store currently supports one local account, and applications do not yet have per-app permission prompts or a complete sandbox. Do not treat the login screen, user-process isolation, or storage as a complete security boundary. The system is not intended to protect sensitive information or resist a hostile physical user.

## Version and wallpaper

The release version is **0.9.6b (0.9.6 Beta)**. The graphical desktop and applications use the `VER` macro in [`src/tak.h`](src/tak.h); the legacy VGA console uses the matching `TAK_VERSION` string in [`src/kernel.c`](src/kernel.c) (warning, i accidentally managed to make the version setting really weird, you may have to change the version number manually in some other stuff, for example the `uname` reply in `src/proc.c` has it hardcoded too).

The default wallpaper is generated by the window manager in [`src/wm.c`](src/wm.c). It shows the Astros logo without a superimposed kernel-version label. Choosing a custom wallpaper (the `wall` terminal command or settings) changes the desktop image, not the reported kernel version. Rebuild the kernel and boot the rebuilt image to see source changes.

The graphical text renderer uses a grayscale DejaVu Sans Mono Bold atlas for antialiased ASCII at normal and enlarged sizes, while retaining the VGA bitmap font for unsupported non-ASCII characters. The atlas redistribution terms are included in [`src/font_smooth_LICENSE.txt`](src/font_smooth_LICENSE.txt).

The installer creates a 128 MiB FAT32 EFI/boot partition and a BFRUS partition (MBR type `0xDA`). GRUB's BIOS and UEFI images embed the read-only BFRUS driver and load `/boot/kernel.elf`, `/boot/initrd.tar`, and `/boot/grub/grub.cfg` from BFRUS. The EFI partition contains the firmware loader. On startup the kernel mounts the BFRUS partition at `/disk`; account homes and saved desktop settings are stored at `/disk/home/<username>`. The live session uses a temporary in-memory home; its files and settings are discarded at shutdown.

BFRUS v1 uses 4 KiB blocks, a fixed inode/extent table, and checksummed metadata. It writes data and metadata directly in place: it has **no journal, copy-on-write, snapshots, compression, or atomic writes**. A power loss or device failure during an update can therefore leave a damaged file or filesystem. BFRUS is experimental and unfinished, it should not be trusted with important data.

## Build and run

The build uses a GNU-compatible C toolchain targeting x86-64, GNU binutils, GRUB 2.14 utilities and source, `xorriso`, and QEMU for emulation. The GRUB source tree is only needed for the installer's boot images (`grubimgs`), which include the custom BFRUS module; the helper modifies the tree to register that module, so use an extracted, disposable copy. The `make run` target launches QEMU.

On Ubuntu or WSL, install the common build dependencies:

```
sudo apt update
sudo apt install build-essential gcc-x86-64-linux-gnu binutils-x86-64-linux-gnu \
  grub-common grub-pc-bin grub-efi-amd64-bin xorriso mtools qemu-system-x86 \
  bison flex gettext autopoint pkg-config
```

Extract GRUB 2.14, build the installer's GRUB images, then build the ISO:

```
make CROSS=x86_64-linux-gnu- GRUB_SOURCE=/path/to/grub-2.14 grubimgs
make CROSS=x86_64-linux-gnu- iso
```

Run `grubimgs` before `iso`, because the initrd picks the images up when it is built. If `build/initrd.tar` already exists, delete it first so it gets rebuilt. Without `grubimgs` the ISO still builds and boots, but without the bootloader images the installer copies to disk.

The ISO is written to `build/astros.iso`. To build and boot it in QEMU:

```
make CROSS=x86_64-linux-gnu- run
```

`grubimgs` builds the BFRUS module for you; it can also be built alone with `make GRUB_SOURCE=/path/to/grub-2.14 grub-bfrus-modules`.

The build can also be opened and edited in VS Code while using WSL as the Linux build environment. The Windows GitHub website is useful for viewing and editing files, but compiling and booting the OS requires a local toolchain or another configured build environment.

## Editing the kernel

1. Open the repository root in VS Code (or edit the source through the GitHub website).
2. Make kernel changes in the relevant files under `src/`. For example, kernel-wide definitions live in `src/tak.h`, startup is in `src/kmain.c`, the window manager is in `src/wm.c`, and task/process code is in `src/proc.c`.
3. Keep declarations in the matching headers and follow the existing freestanding C patterns. The kernel is built with warnings treated as errors (`-Werror`).
4. Rebuild the ISO using the command above, then boot it in QEMU before testing on physical hardware. Changes to boot, disk, or installer code should be tested especially carefully; installer operations can modify disks.
5. If changing a user application, edit its source in `apps/` or the shared runtime in `sdk/`, then build the applications and ISO:

   ```
   make CROSS=x86_64-linux-gnu- apps
   make CROSS=x86_64-linux-gnu- iso
   ```

The Makefile discovers C files directly under `src/` automatically, except `src/stbimg.c`, which has its own build rule, and `src/term.c`, which is skipped. New code should be added to the existing build structure rather than committed generated files from `build/`.

## User executable formats

Native TAK-only applications use `.te` files. Their `TE02` header and `int 0x80` service ABI are specific to TAK; `build/apps/*.elf` files produced while building these applications are intermediate linker outputs, not Linux programs.

Separately, the kernel can load x86-64 ELF64 `ET_EXEC` and `ET_DYN` images from the filesystem. ELF files can be launched from the file manager or terminal (for example, `run /bin/program`); the `.elf` suffix is optional because the loader checks the ELF magic. Put executable files in the initramfs under `/bin` or `/apps`, and their shared objects under `/lib`. The loader supports loadable segments, a Linux-style initial stack, `DT_NEEDED` libraries found under `/lib`, GNU or System V symbol tables, and the common `R_X86_64_RELATIVE`, `R_X86_64_64`, `R_X86_64_GLOB_DAT`, and `R_X86_64_JUMP_SLOT` relocations.

This remains a limited ELF loader and Linux compatibility layer. Linux x86-64 ELF programs use a `SYSCALL`/`SYSRET` entry path and per-task floating-point/SSE and FS/GS base state. The implemented syscalls are `read`, `write`, `mmap`, `mprotect`, `munmap`, `brk`, `sched_yield`, `madvise` (only the free/dontneed cases, which zero the pages), `nanosleep`, `getpid`/`gettid`, `exit`/`exit_group`, `uname` (it reports the TAK version), `arch_prctl` (FS/GS base), `set_tid_address`, `clock_gettime` (monotonic clocks only) and `clock_getres`, `set_robust_list`, `prlimit64` (queries only), and `getrandom`. Anything else returns `ENOSYS`, including `gettimeofday`, `time`, and `rseq`.

ELF images must fit TAK's reserved user address range. Linux programs with `PT_INTERP` are rejected: there is no Linux dynamic linker/runtime loader, and file-backed mappings, `openat`, `execve`, `fork`/`clone`, signals, full futex/thread support, and the Linux socket ABI are not implemented. The syscall subset is not sufficient to run ordinary glibc/musl applications, Steam, or games. Linux networking, TLS, and Steam connectivity remain future work; the existing TCP client is a single bounded kernel connection, not a POSIX socket service.
